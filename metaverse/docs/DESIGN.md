# 三浦塾 2Dメタバース教室 設計書

最終更新：2026-11-15（第1段階 実装時点）

---

## 1. 推奨する技術構成と選定理由

| 層 | 採用技術 | 理由 |
| --- | --- | --- |
| 画面（クライアント） | HTML + Canvas 2D + 素の JavaScript（PWA） | ビルド不要で軽く、古めのスマホでも動く。2D の見下ろし型マップは Canvas で十分高速。PWA にすればホーム画面に追加してアプリのように使える |
| サーバー | Node.js 22 + Express | 画面とAPIを1つのサーバーで配信できる。第2段階のリアルタイム同期（Socket.IO）も同じ言語・同じプロセスで書ける |
| リアルタイム同期（第2段階〜） | Socket.IO（WebSocket） | アバター位置・入室状況・挙手を低遅延で同期。切断の検知・自動再接続が標準で付いている |
| 音声・画面共有（第3段階〜） | **LiveKit（SFU）** | 45人規模では「参加者どうしが直接つなぐ方式（P2P）」は端末の負荷と通信量が大きすぎて成立しない。SFU なら先生は1本送るだけで全員に届く。<br>LiveKit はトークンに「話してよいか・画面共有してよいか」を埋め込めるので、**権限をサーバー側で強制**できる。iOS Safari / Android Chrome に対応した JS SDK があり、TURN も内蔵。録画（Egress）は明示的に起動しない限り行われない |
| データベース | 第1段階：SQLite（Node.js 標準の `node:sqlite`）<br>本番：PostgreSQL を推奨 | 開発・小規模運用は追加インストール不要の SQLite で十分。複数サーバー構成やバックアップ運用を考えると本番は PostgreSQL（SQL はほぼそのまま移行可能） |
| 認証 | ID + パスワード、サーバー側セッション（HttpOnly Cookie） | 小中学生がメールアドレスを持っていない前提。トークンをJSに渡さないので盗まれにくい。オーナーが強制ログアウトできる |

### 採用しなかった案
- **P2P（WebRTC メッシュ）のみ**：初期試作（`virtual-classroom/`）で使用。少人数なら動くが、15人教室×3では成立しないため不採用。
- **Zoom / Google Meet の埋め込み**：アプリ内の「誰と話せるか」を細かく制御できず、個別通話との切り替えも外部アプリ任せになるため不採用。
- **Unity / Phaser 等のゲームエンジン**：見た目は作りやすいが、今回の規模ではファイルサイズと学習コストに見合わない。

## 2. 外部サービスと概算月額費用

> 金額は 2026年11月時点の目安です。**各社の料金ページで最新の価格を必ず確認してください。** 1ドル=150円で換算。

| サービス | 用途 | 目安（月額） |
| --- | --- | --- |
| アプリのサーバー（Render / Fly.io / Railway など） | 画面・API・リアルタイム同期 | 1,000〜4,000円 |
| PostgreSQL（Neon / Supabase / Render など） | ユーザー・権限・設定 | 0〜4,000円（小規模なら無料枠あり） |
| LiveKit Cloud | 音声・画面共有 | 検証は無料枠。本番は有料プラン＋利用量課金で **数千〜2万円程度** を想定 |
| （代替）LiveKit を自前のVPSで運用 | 同上 | 3,000〜10,000円（4コア/8GB 程度＋通信量）。運用の手間が増える |
| 独自ドメイン | 例：class.miurajuku.jp | 100〜300円相当（年払い） |
| SSL証明書 | 通信の暗号化 | 0円（ホスティング側で自動発行） |

**合計の目安：月 5,000〜25,000円**（授業時間・人数・画面共有の量で変動）

利用量の見積もり例：生徒45人 × 1日2時間 × 月20日 ＝ 約108,000 参加者分/月。音声中心なら通信量は小さく、画面共有の視聴が多いほど増えます。第5段階の負荷テストで実測して、プランを決めるのが安全です。

## 3. スマートフォンで実現できる機能と制約

| 機能 | iPhone（Safari） | Android（Chrome） | 備考 |
| --- | --- | --- | --- |
| 2D空間の移動（タッチ） | ○ | ○ | タップ移動＋バーチャルスティック（第1段階で実装済み） |
| 音声を聞く・話す | ○ | ○ | 最初の1回は画面タップが必要（ブラウザの自動再生制限）。マイクは毎回ブラウザの許可ダイアログが出る |
| 先生の画面共有を見る | ○ | ○ | 通信量が増える（目安：1時間で数百MB）。Wi-Fi 推奨 |
| **生徒のスマホから画面共有** | **×** | **×** | スマホのブラウザは画面共有（getDisplayMedia）に対応していない |
| カメラ映像を送る | ○ | ○ | 背面カメラでノートを映すことは可能 |
| バックグラウンドでの通話 | △ | △ | 画面ロック・アプリ切り替えでマイクが止まる場合がある → 自動再接続で対応 |
| ホーム画面に追加（PWA） | ○ | ○ | iPhone は Safari の「共有→ホーム画面に追加」 |
| プッシュ通知 | △ | ○ | iPhone はホーム画面に追加した場合のみ（iOS 16.4以降） |

### 生徒の画面共有ができない場合の代替案
1. **カメラでノートを映す**（第4段階で実装予定）：個別通話中に「ノートを見せる」ボタン → 背面カメラの映像を先生だけに送る。いちばん手軽。
2. **写真を撮って先生に送る**：個別通話中に撮影した写真を先生だけが見られる。通信が弱くても使える。
3. **パソコン・タブレットからの参加**：PCのブラウザなら画面共有可能。
4. **将来：ネイティブアプリ化**（Capacitor 等で包む）すれば、iPhone の ReplayKit / Android の MediaProjection で画面共有が可能になる。開発・審査コストが大きいので、必要性が確認できてから検討。

その他の注意点
- イヤホン（有線・Bluetooth）を推奨。スピーカーだとハウリングや周りの音が入りやすい。
- 古い端末（目安：iOS 15 未満、Android 9 未満）は動作対象外とするのが安全。

## 4. 画面構成とデータベース設計

### 画面構成

| 画面 | 内容 | 状態 |
| --- | --- | --- |
| ログイン | ID・パスワード。ユーザーが0人のときは「初期設定（オーナー作成）」を表示 | ✅ 第1段階 |
| 2D空間（メイン） | 見下ろし型マップ・自分のアバター・現在地と定員・「へやをえらぶ」「すわる」・ズーム・スマホ用スティック | ✅ 第1段階 |
| 部屋えらび | 教室1〜3・自習室・ロビー。入れない教室は🔒 | ✅ 第1段階（人数表示は第2段階） |
| 管理：ユーザー | 先生・生徒の登録／編集／無効化／強制ログアウト／パスワード再発行 | ✅ 第1段階 |
| 管理：権限 | ユーザーごとのチェックボックス（6項目）・先生の担当教室 | ✅ 第1段階 |
| 管理：教室の設定 | 各部屋の定員（座席数が上限） | ✅ 第1段階（定員による入室制限は第2段階） |
| 管理：操作ログ | ログイン・管理操作の記録 | ✅ 第1段階 |
| 管理：入室状況 | 各教室の人数・入室者・接続の切断 | ⏳ 第2段階 |
| ほかの人のアバター・人数表示 | 位置同期・入退室 | ⏳ 第2段階 |
| 挙手・リアクション（生徒）／挙手一覧（先生） | | ⏳ 第2段階 |
| 授業バー（先生） | 全体通話・画面共有の開始／終了 | ⏳ 第3段階 |
| 画面共有ビューア | 先生の画面を大きく表示 | ⏳ 第3段階 |
| 個別通話 | 参加確認 → 個別通話画面 → 授業に戻る | ⏳ 第4段階 |

### データベース（実装済み）

```
users            ユーザー
  id, login_id(一意), display_name, role(owner/teacher/student),
  password_hash(scrypt), avatar_color, is_active, created_at, updated_at

permissions      ユーザーごとの権限（チェックボックス6項目）
  user_id, can_enter_classroom, can_start_class_call, can_start_private_call,
  can_share_screen, can_handle_students, can_manage_classroom

rooms            部屋と定員
  id(class1/class2/class3/study), name, type(classroom/study),
  capacity(定員), max_capacity(座席数), sort_order

teacher_rooms    先生の担当教室
  user_id, room_id

sessions         ログイン中の端末（トークンはハッシュで保存）
  token_hash, user_id, created_at, expires_at, ip, user_agent

audit_logs       操作ログ
  id, at, actor_id, action, target, detail, ip
```

個人情報は「表示名・ログインID・役割・アバターの色」だけを保存します。メールアドレス・住所・学校名などは持ちません。表示名は名字だけ・ニックネームを推奨（管理画面にも案内を表示）。

### 追加予定のデータ
- **入室状況・挙手**：サーバーのメモリ上で管理（DB には保存しない）。サーバーを複数台にする場合は Redis に移す。
- `call_logs`（第3・4段階）：通話の開始・終了時刻と参加者のみを記録。**音声・映像・画面の録音／録画は保存しない**。

## 5. 段階的な実装計画

| 段階 | 内容 | 主な確認方法 |
| --- | --- | --- |
| **第1段階** ✅ | 2D空間・教室3部屋（各15席）・自習室（32ブース）・アバター移動（キー／タップ／スティック）・ログイン・ユーザー登録・権限設定・定員設定・操作ログ・PWA | `npm test`（APIの権限チェック13項目）＋ブラウザでの操作確認（README 参照） |
| 第2段階 | Socket.IO 接続（Cookie で認証）・ほかの人のアバター表示と位置同期・**サーバー側での入室チェック（権限＋定員）**・座席の取り合い防止・入室人数と入室者一覧・挙手／取り消し／リアクション・先生への挙手通知・管理者による接続の切断 | 端末3台以上で同時ログインし、定員を2人にして3人目が入れないこと、挙手が先生に届くことを確認 |
| 第3段階 | LiveKit 導入・トークン発行API（権限がある先生にだけ「話す・画面共有」の許可を発行）・先生の全体通話／画面共有の開始・終了・生徒側の画面共有ビューア・音声開始のタップ案内 | 先生PC＋生徒スマホ2台で、担当教室の生徒にだけ声と画面が届くこと、ほかの教室には届かないこと |
| 第4段階 | 個別通話（先生が生徒を選択 → 生徒に参加確認 → 別の通話部屋へ）・個別通話中は全体授業の音声を自動で止める・先生の全体マイクも自動で一時停止・個別の画面共有（先生→生徒）・生徒は「カメラでノートを見せる」・終了で授業へ戻る | 個別通話の声がほかの生徒に聞こえないこと、終了後に授業の音声が戻ること |
| 第5段階 | スマホ実機での操作性改善・45人同時接続の負荷テスト（自動化した疑似クライアント）・音声品質の確認・セキュリティ点検（権限のすり抜け・総当たり・XSS 等） | 負荷テスト結果のレポート、チェックリスト |

### 全体授業と個別通話を混ぜないための設計（第3・4段階で実装）
- 教室ごとに LiveKit の「部屋」を分ける（`class1` など）。個別通話は毎回新しい部屋（`private-xxxx`）を作る。
- 生徒の教室用トークンは「聞くだけ」。発言は先生が挙手した生徒に許可したときだけ、サーバーが権限を変更する。
- 個別通話に入った生徒の端末は、教室の音声の受信を止める。先生の端末は、教室向けのマイクを自動で止めてから個別の部屋に入る。
- 生徒どうしで個別通話を始める API は存在させない（サーバーが先生の権限を確認してからトークンを発行）。
